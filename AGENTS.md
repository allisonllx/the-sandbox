# AGENTS.md

This repository is designed for long-running coding-agent work. The goal is not
to maximize raw code output. The goal is to leave the repo in a state where the
next session can continue without guessing.

## Startup Workflow

Before writing code:

1. Confirm the working directory with `pwd`.
2. Read `claude-progress.md` for the latest verified state and next step.
3. Read `feature_list.json` and choose the highest-priority unfinished feature.
4. Review recent commits with `git log --oneline -5`.
5. Run `./init.sh`.
6. Run the required smoke or end-to-end verification before starting new work.

If baseline verification is already failing, fix that first. Do not stack new
feature work on top of a broken starting state.

## Working Rules

- Work on one feature at a time.
- Do not mark a feature complete just because code was added.
- Keep changes within the selected feature scope unless a blocker forces a
  narrow supporting fix.
- Do not silently change verification rules during implementation.
- Prefer durable repo artifacts over chat summaries.

## Challenge artifact consistency

The challenge brief and starter files are generated by **different modules**. They
drift easily if you only update one side. This bug has recurred — treat it as a
required check, not optional polish.

**Single source of truth (dynamic technical path):** `TechnicalChallengeSpec` on
`BacklogItem.challenge_spec` — projected to Micro-PRD via `spec_to_microprd()`,
starter tree via `generate_scaffold_from_spec()`, and blueprint via
`spec_to_blueprint()`. Legacy `demo-*` items use `legacy_spec_adapter` at read
time without mutating seeds.

**These must all agree on edit targets and public API symbols:**

| Surface | Where |
|---|---|
| Spec | `challenge_spec.interface_contract` + `starter_layout.edit_targets` |
| Interface doc | `docs/SPEC.md` in starter package |
| Tests | `tests/test_public.py` imports from `interface_contract.public_api` |
| Micro-PRD | `context` (markdown brief), `definition_of_success`, `structural_constraints`, `sandbox_instructions` (from spec projection) |
| Spec examples | `challenge_spec.examples[]` — typed signatures + literal I/O; projected into brief + `docs/SPEC.md` |
| Starter README | `README.md` inside the package |
| Student API | `GET /api/v1/sandbox/challenges/{id}` → `microprd` + `starter` file tree; frontend renders brief markdown |
| Legacy demos | `starter_scaffold.py` — only path that legitimately uses `src/queries.py` |

**When you change** archetypes, scaffolds, or student-facing copy:

1. Update `archetype_catalog.py` / `scaffold_interpolate.py` — do **not** hardcode
   function names in static template test files.
2. Run Preview → Publish (or `./scripts/samples/run_archetype.sh <name>`) and confirm
   brief, SPEC.md, and editor file tree match.
3. Extend `test_challenge_spec.py`, `test_scaffold_interpolate.py`, and
   `test_challenge_factory.py` when adding archetypes or changing inference.

**Browser workspace must be sufficient:** students work in the in-browser editor.
Spec-driven packages require **docs/SPEC.md**. SQLite archetypes also need
**docs/DATA.md**; mount the dataset on **Run Public Tests**.
See `challenge_factory/workspace_sufficiency.py`.

See `backend/challenge_factory/DOCS.md` and `scripts/samples/DOCS.md`.

## Documentation Sync

When you change code, update related documentation **in the same session** — do not
leave docs stale for the next session. Treat this as mandatory at **end of every
session** and after any **meaningful verification run** (pytest, factory scripts,
smoke tests) that changes behavior or reveals drift.

1. **Module doc** — check `<folder>/DOCS.md` for every code folder you edited
   (e.g. `backend/api/` → `backend/api/DOCS.md`; `scripts/` → `scripts/DOCS.md`)
2. **Topic docs** — if behavior, API contracts, architecture, or user flows
   changed, check the relevant files in `docs/` (see `docs/documentation-sync.md`)
3. **Root `README.md`** — update when Quickstart, project structure, or the API reference
   table changes (the only repo-level `README.md`)
4. **Prompts** — if you change LLM behavior, archetypes, hot-path flow, or JSON
   contracts, update the matching file in `backend/prompts/` and
   `backend/prompts/DOCS.md`. Keep `challenge_spec.py` aligned with
   `archetype_catalog.py` trigger rules. Mark legacy prompts (`blueprint_planner.py`,
   `microprd.py` TECH, `scaffold_technical.py`) when they are off the hot path.

If no doc or prompt updates were needed, record
`"Docs: no update required — <reason>"` in `claude-progress.md`. Do not skip the
check silently.

## Required Artifacts

Keep these current — they are how the next session (human or agent) restarts
without guessing:

| Artifact | When to update |
|---|---|
| `feature_list.json` | Feature status, evidence, verification notes — when scope or done-ness changes |
| `claude-progress.md` | **Every session end** and after significant runs — verified state, next step, docs/prompts sync note |
| `init.sh` | When startup or default verification path changes |
| `session-handoff.md` | Optional compact handoff for larger or interrupted sessions |
| `backend/prompts/*.py` | When LLM contracts, archetypes, or pipeline stages change (same session as code) |
| Module `DOCS.md` + `docs/` | Same session as code (see **Documentation Sync** above) |

## Definition Of Done

A feature is done only when all of the following are true:

- the target behavior is implemented
- the required verification actually ran
- evidence is recorded in `feature_list.json` or `claude-progress.md`
- related `DOCS.md`, `docs/`, and `backend/prompts/` updated when behavior,
  contracts, or LLM flows changed (see `docs/documentation-sync.md`)
- challenge artifact consistency verified when factory, Micro-PRD, or starter
  scaffolds changed (see **Challenge artifact consistency** in `AGENTS.md`)
- the repository remains restartable from the standard startup path

## End Of Session

Before ending a session — **and after any standalone factory/script run you used
to validate behavior** — complete this checklist:

1. **`claude-progress.md`** — new session entry: goal, what changed, verification
   command + result (e.g. `160 passed`), docs/prompts sync note, next step, blockers.
2. **`feature_list.json`** — mark features passing/failing with evidence; do not
   mark complete without verification.
3. **Documentation sync** — module `DOCS.md`, `docs/`, `README.md` if needed; record
   `"Docs: no update required — …"` when nothing applied.
4. **Prompts sync** — if hot path or archetypes changed, update `backend/prompts/`
   and `backend/prompts/DOCS.md`; otherwise note `"Prompts: no update required"`.
5. Record any unresolved risk or blocker.
6. Commit with a descriptive message once the work is in a safe state (when the
   user asks for a commit).
7. Leave the repo clean enough for the next session to run `./init.sh` immediately.

## Constraints

### Zero-Trust Data Boundary (Critical)
- The Local Privacy Proxy MUST run entirely client-side. Raw corporate data (logs,
  user records, PII, API keys, JWT tokens) must NEVER be transmitted to any
  external API, cloud service, or database.
- PII scrubbing must complete before any data leaves the local process boundary.
- Any code path that could leak raw data to an external LLM must be blocked with
  an explicit guardrail check and a hard error.

### Security & IP
- Student-submitted code runs only inside ephemeral, isolated containers (e.g.
  Docker with no network access and resource limits). Never execute student code
  in the host environment or in a shared process.
- Startup schema, variable names, and business logic must pass through the
  Relaxation Control (noise injection + variable mapping) before being published
  to the public challenge layer.

### Data & AI
- External LLM APIs (OpenAI, Anthropic, etc.) may only receive anonymized
  structural metadata, never raw content rows or PII.
- Synthetic datasets generated by the platform must be structurally equivalent
  to the real data but statistically distinct — confirm this with a distribution
  check before publishing a challenge.

### Development
- Python 3.11+ for all backend and privacy-proxy code.
- No new third-party dependencies without explicit approval — add to
  `requirements.txt` or `package.json` and note the reason in the PR description.
- Secrets (API keys, DB credentials) must use environment variables; never
  hard-code them or commit `.env` files.
- Never run `git push --force` or drop production database tables without an
  explicit user instruction.
